# LIBERIA360 Web

Next.js (App Router) frontend — a single responsive codebase for mobile, tablet, and desktop.

## Setup

```bash
cp .env.example .env.local
npm install
```

Requires the API (`../api`) running — see `../api/README.md`.

**Codespaces**: the default `NEXT_PUBLIC_API_URL` only works for server-rendered pages. Client-side requests (auth, form submissions) need it pointed at port 3001's forwarded URL — see the root `README.md`'s Codespaces section.

## Run

```bash
npm run dev     # http://localhost:3000
```

## Tests

```bash
npm run test
npm run test:watch
```

Jest + React Testing Library, via `next/jest`. Covers `lib/*` utility functions, `localStorage`-backed modules (`auth-storage`, `saved-places`), HTTP error normalization, and component rendering.

```bash
npm run test:e2e
```

Playwright, against a real running API + database — see [`e2e/README.md`](./e2e/README.md) for what's covered and how to run it.

## Build

```bash
npm run build
npm run lint
```

## Architecture

- **Data fetching**: server components fetch directly from the API for public, unauthenticated pages (catalog, counties, search). Authenticated pages and mutations are client components — auth state lives in `localStorage` (`src/lib/auth-storage.ts`), not a cookie, so there is no server session to read from a server component.
- **HTTP layer**: `src/lib/api.ts` (`apiFetch`) handles unauthenticated server-side reads; `src/lib/http.ts` (`apiRequest`) plus per-resource `*-api.ts` modules handle authenticated client-side writes, normalizing API error responses into a single `HttpError(status, message)`. That `message` is the raw backend string — every `NotFoundException` in the API embeds the record's raw id/slug (`Itinerary "e576ae27-…" not found`), exactly right for a server log and never something to put in front of a user. `src/lib/errors.ts`'s `getFriendlyErrorMessage(err, options)` is the translation layer: it always overrides a 404 (with a per-call-site `notFoundMessage`, or a generic default), leaves 400/403/409/422 alone since those are already written to be read by a person, maps 429/5xx/network failures to generic copy, and reports the real error to Sentry either way (`error-reporting.ts`, no-op unless configured) so a translated-away message is still visible to developers. `isNotFoundError(err)` is the companion check for the common case where a 404 on a *delete* should be treated as an already-achieved success rather than an error (the resource being gone is the outcome the user wanted) — see the trip deletion flow below. Every catch block that ends in `setError(...)` should go through this rather than reading `err.message` off an `HttpError` directly.
- **Destructive actions**: `src/components/ConfirmDialog.tsx` replaces `window.confirm()` everywhere something permanent happens (delete a trip, leave a shared trip, remove business content, ...) — title, consequences, an "this action cannot be undone" line, Cancel, and a loading state on confirm, all styled to match the rest of the app. Pass `confirmationPhrase` (the item's name) to require the user to type it before the confirm button enables, reserved for especially destructive cases — see the trip deletion flow (`app/trips/page.tsx`, `app/trips/[id]/page.tsx`) for the threshold used (a trip with several saved stops, or any collaborators).
- **Shared types**: `src/lib/types.ts` re-exports `@liberia360/shared-types`, a local npm workspace package holding the canonical response shapes for every API resource.
- **Styling**: Tailwind CSS (`tailwind.config.ts`); brand palette (`brand`, `accent`, `gold`, `flag`) sourced from the logo.
- **Theme (light/dark)**: class-based (`darkMode: 'class'`), not OS-media-based — a user's explicit choice has to win over `prefers-color-scheme`. `src/lib/theme-storage.ts` holds the state (same localStorage + custom-event pattern as `auth-storage.ts`, no React context); `src/hooks/useTheme.ts` wraps it; `ThemeToggle` (in the header, every page) flips it. An inline blocking script in `layout.tsx`'s `<head>` applies the `dark` class before first paint, so there's no flash of the wrong theme on load. New components should pair light Tailwind classes with a `dark:` variant rather than assume a fixed background — check `content-shared.tsx` or `Header.tsx` for the established slate/brand/amber tint mappings.
- **Maps**: Leaflet, category markers colored via a deterministic hash. Tiles are served from CARTO's free basemap CDN (`basemaps.cartocdn.com`, still OSM-sourced data, dual attribution), not raw `tile.openstreetmap.org` — OSM's own tile servers explicitly aren't meant for production traffic and can silently rate-limit or block requests; CARTO's tiles are the same map served from infrastructure meant to be hit this way, with no API key needed. All three map components (`/explore`, the destination-page mini map, and the admin location picker below) use this tile source. Admin > Content > Places' location picker (`admin/content/PlaceLocationPicker.tsx`, also used by the self-service `PlaceSubmissionForm`) replaces raw lat/lng number entry with click/drag-to-place-a-pin, plus two more ways to land on the same spot: a "Use my current location" button (`navigator.geolocation`) for a submitter standing at the place right now, and manual latitude/longitude entry for anyone who already has exact coordinates from elsewhere (a GPS device, a shared map pin) — all three set the same `onChange`, so nothing downstream cares which one produced the value. Its address/landmark search box is a pure enhancement on top of that, only rendered when `NEXT_PUBLIC_MAPBOX_TOKEN` is set (Mapbox Geocoding API, scoped to Liberia); unset, the picker still works fully by click/drag, current-location, or manual entry.
- **Creator profiles**: full self-service profile (`/creators/me`) — category, home county, contact/social links, languages, experience, certifications, availability, plus a portfolio gallery (`CreatorPortfolioManager`/`CreatorPortfolioGallery`, images via the upload pipeline + external video links only, no self-hosted video) and services/experiences (`CreatorOfferingsManager`). `CreatorCard` is the shared discovery card (directory, and anywhere else a creator surfaces); `/creators/[username]` is the public profile. `verified` is an admin-set trust badge (Content > Creators tab), not self-service. Reviews, profile analytics, and inquiries/bookings all work for creators too now (mirroring businesses), surfaced on `/creators/[username]` and `/creators/me`.
- **Images**: `SafeImage` (`src/components/SafeImage.tsx`) wraps every uploaded photo — a caller-supplied fallback on load failure, a pulsing skeleton look while loading, and an optional `thumbSrc` (`lib/images.ts`'s `resolveThumbUrl`) that loads the small pre-shrunk rendition the upload pipeline saves alongside every full-size image (see `api/README.md`'s Uploads section), falling back to the full image if no thumbnail exists. The skeleton is applied to the *same* `<img>` element (a background color + `animate-pulse`, not a separate `hidden` sibling) — a `loading="lazy"` image only starts fetching once the browser can measure a real layout box for it, so hiding it via `display: none` would have permanently prevented that fetch from ever firing.
- **PWA**: `public/manifest.webmanifest` + `public/sw.js` (app-shell caching, push notification handlers). Saved places are snapshotted to `localStorage` for offline access, independent of the service worker's HTTP cache. `SplashScreen` (`src/components/SplashScreen.tsx`), mounted first in `layout.tsx`'s `<body>`, shows a brand splash on a real page load (server-rendered, so it paints before any JS runs) and hides itself once hydration completes — the root layout only mounts once per hard navigation, so it never reappears on client-side route changes.
- **App icon / launch splash assets**: `logo.png` (the full circular seal — make, capitol, waterfall, wordmark, tagline) is a letterhead-style lockup with a huge white margin baked in, no alpha channel. Used directly as a raw square, it produces an ugly white box wherever it sits on the brand-navy background — most visibly the OS-generated PWA launch splash (Android/Chrome draw the manifest's `icons` entry straight over `background_color`), which showed exactly that box before this fix. `public/icons/icon-{192,512}.png` and `src/app/icon.png` are now a tightly cropped "medallion" derived from `logo.png` (emblem art + wordmark only — the tiny pictogram row and two lines of tagline text are illegible at icon sizes, so they're dropped) on a transparent background with a soft drop shadow, so it floats cleanly on navy instead of sitting in a box. `public/icons/icon-{192,512}-maskable.png` and `src/app/apple-icon.png` are the same medallion full-bled onto an opaque navy square (maskable icons must never rely on transparency — Android crops them into circle/squircle/rounded-square per launcher, and iOS fills a transparent touch icon with black), with the medallion kept inside the ~75% safe zone so no launcher's mask clips it. Regenerating these from `logo.png` again (a future rebrand, say) means re-running the crop/composite pipeline that produced them — there's no separate source file, only the derived PNGs.
- **SEO**: schema.org JSON-LD on destination and event pages (`src/lib/structured-data.ts`).
- **Crash reporting**: `@sentry/browser` (client-side errors only), no-op unless `NEXT_PUBLIC_SENTRY_DSN` is set.
- **Self-service place submissions**: any signed-in user can add a destination that isn't in the catalog yet (`/places/submit`, `PlaceSubmissionForm` — same field set as the admin's Content > Places create form, including the map location picker and photo manager). Submitting auto-claims the new place as the submitter's own `Business` in the same request (see "Business owner dashboard" below), so the confirmation screen links straight into that business's dashboard rather than a separate tracking page — there's no standalone "My Places" area any more; a submission is tracked and edited from that dashboard's **Place Details** tab (`PlaceDetailsManager`) instead. A submission is invisible to the public catalog until an admin approves it (`Place.reviewStatus`, mirroring the Business self-claim review lifecycle above); editing a rejected submission auto-resubmits it, same as a rejected business claim. Admin > Content > Places (`PlacesTab.tsx`) now filters by review status and opens each place by id; anything not yet approved — or ever self-submitted — surfaces `PlaceReviewPanel` above the regular edit form: the full submission as the submitter provided it (every photo, description, location on a map link, contact info, tags, cost estimates) plus contextual decision actions (approve / request changes / reject / suspend, each with an optional reason), not a bare verify/unverify toggle.
- **Self-service events**: `NewEventForm` (behind `/events/new`, gated by the same claimed-business/creator-profile/admin eligibility check as `POST /events`) is dual-mode — the same component also edits an event already posted, when an `event` prop is passed. Organizers manage what they've posted from `/account/my-events` (`GET /events/mine`, includes past events unlike the public listing), and the public event detail page shows an `EventOwnerActions` bar (edit link + cancel button with the standard `ConfirmDialog`) to whoever posted it or an admin. Events now carry photos (`PhotoManager`, same as places/businesses) shown on both the list card and detail page. `GET /events` hides events whose `startDate` has already passed by default (previously they sorted to the top forever, ahead of anything upcoming) — the admin Content > Events tab opts back in with `includePast=true` since it still needs to reach them. The events list also has "Today / This weekend / This month" quick filters (`EventFilters`, date-range math in `lib/date-ranges.ts`) that set `dateFrom`/`dateTo` on the existing query. **Events now go through the same review-gate as a self-submitted Place/Advertisement** (`Event.reviewStatus`, added after self-service posting shipped with no moderation step at all — any claimed business or creator could publish straight to the public listing with nothing ever reaching an admin) — a submission starts pending and is invisible on the public listing until an admin approves it from the Moderation page's "Pending events" queue or the Content > Events tab's status column/`EventReviewStatusControl`; an event created directly by an admin publishes immediately. `/account/my-events` shows the organizer their event's status badge plus, when rejected, the admin's reason inline. The "events nearby" push notification (to residents who set that event's county as home) now fires only once the event is actually approved, not at submission time. Home's `EventCarousel` (`src/components/EventCarousel.tsx`/`EventCard.tsx`) surfaces approved upcoming events right after Trending Places — previously a plain text list at the very bottom of the page, below the ad carousel, which also meant it silently rendered nothing at all whenever there were zero approved events on hand (the common case right after the review-gate above shipped). It reuses `AdvertisementBanner`'s exact snap-scroll drag/arrow/dot carousel mechanism for this organic content instead of paid ads. `EventCard` (a carousel slide) matches `EventFeedCard`'s (the Events listing's full-width card) own image-top/white-content-below composition rather than a different full-bleed-overlay treatment, so the two don't read as separate features: cover photo, then a live emerald "Happening now" pill (same convention `PlaceKeyFacts`' "Open now" badge uses) when the event's already started, else the plain date/time; title; location; a "X going" count; and the same Interested/Share action row `EventFeedCard` already has (`EventRsvpButtons` variant `"feed"` + `ShareMenu` variant `"feed"`) — a card someone can act on right from the shelf instead of only linking through. The Events listing page (`/events`) now opens with its own **Featured events** shelf — the exact same `EventCarousel`/`EventCard`, just re-labeled (`title="Featured events"`, no redundant "See all" back to the page it's already on) and fed the same "top 8 upcoming, unfiltered" set Home's carousel shows; it only fetches on an unfiltered first-page landing, not on every filtered/paginated request for the list below it. `/account/my-events` now has a "View metrics" toggle per event (mirrors `/account/my-ads`'s own metrics panel) — a page-view count from the new `GET /analytics/event/:eventId` (event is a fourth `AnalyticsEvent` target alongside place/creator/advertisement) alongside the interested/going counts already denormalized on `Event` itself, so an organizer can see how their event is actually doing instead of nothing at all. `EventViewTracker` (previously only updating "recently viewed") now also fires the `view` analytics event on page load, the same way `PlaceViewTracker`/`AdvertisementViewTracker` already do — without this the view count would stay zero forever.
- **Product review fixes (Aug 2026)**: five gaps found in a team readout of the live product. (1) Place detail pages now lead with `PlaceKeyFacts` (`src/components/PlaceKeyFacts.tsx`) — phone/website/hours/price/directions/verification pulled up near the title, a claimed business's own contact info taking priority over the place's, one primary CTA, and a "Suggest an update" recovery link (a relabeled `ReportButton`) plus "Claim this place" wherever a fact is genuinely missing, instead of a dead-end "Not listed." The stale disabled "Plan Trip (Phase 2)" button is now a real link to `/trips/new?interest=<category>`. (2) Search (`GET /places?q=`) resolves singular/plural and a category-alias table into a category match unioned with the text search, so a query like "beach" that matches no place's own name/description text still returns every place in that category instead of zero results (see `api/README.md`). (3) `/explore`'s map (`ExploreMapClient.tsx`) gained a list companion alongside the pins, a visible result count, a "Clear filters" action, a Leaflet `locate()`-backed "Locate me" control, and `MapFallbackBoundary` — a plain error boundary around the map so a Leaflet/tile failure degrades to the same list instead of a blank pane. (4) `GET /admin/places/data-quality` (`AdminPlacesTab`) flags editorial problems a review-status pass wouldn't catch — starting from a real one found in the deck: a place whose slug no longer matches its current name, left over from an earlier rename, serving the wrong card image under a URL that reads as a different destination. (5) **Guest-first trip planning**: `TripPlannerForm` no longer login-gates the planner. A signed-out visitor submits to the unauthenticated `POST /itineraries/preview` and sees a real generated route immediately (clearly labeled "nothing's saved yet"); "Log in to save this trip" stashes the exact inputs via `src/lib/pending-trip-draft.ts` (sessionStorage, one-time handoff) and sends them to `/login?next=/trips/new`, where the form picks the draft back up the instant they're signed in and saves it automatically by calling the normal `POST /itineraries` with the same inputs — deterministic against unchanged catalog data, so what they previewed is exactly what gets saved.
- **Admin information architecture**: a 7-group collapsible sidebar (`src/lib/admin-nav.ts`) — Dashboard, Analytics, Content, Users & Roles, Settings, Security, System/Operations — driven by a typed capability model (`src/lib/capabilities.ts`) rather than scattered `isAdmin`/`isSuperAdmin` checks. `hasCapability(user, capability)` resolves each capability to a role tier; today that's still just the two real backend tiers (`AdminGuard`/`SuperAdminGuard`), so this is a naming/consistency layer over real enforcement, not a new permissions engine — see `/admin/roles` (Roles & Permissions) for the same map rendered as a reference page. Sections without a real feature behind them yet (Settings, a dynamic Roles editor) render an honest "not built yet" state (`PlaceholderPage` in `admin-ui.tsx`) instead of fake controls. Shared dashboard primitives (`KpiCard` with period-over-period deltas, `Panel`, `EmptyState`, `PeriodToggle`) live in `src/components/admin-ui.tsx`.
- **Advertisements (self-service ad slots)**: any signed-in user can advertise a digital product or their business — no existing Place/Business/Creator listing required — via `/account/my-ads` (`AdvertisementForm`, dual-mode create/edit: type, title, description, price label, photos via `PhotoManager`, WhatsApp/phone/email/link contact methods). Submissions go straight to review (mirrors the self-service place-submission single-step flow, not business content's two-step draft/submit) and are invisible on the public "Sponsored" placements until an admin approves them; editing a rejected ad auto-resubmits it, editing a suspended one does not. Owners see per-ad view and contact-click metrics inline on the My Ads page (reuses the same `AnalyticsEvent` engine as creator/place analytics). Approved ads surface as a clearly labeled "Sponsored" section (`AdvertisementBanner`/`AdvertisementCard`) on the Home page and on page 1 of Search results, rendered as a snap-scrolling carousel of full-bleed slides — same visual treatment as the Featured Destination banner below it (cover photo, bottom gradient, overlaid title) rather than a boxed thumbnail next to a padded text block, so every slide puts its whole card area to work instead of leaving a chunk of it blank. `snap-x`/`snap-mandatory` makes a swipe settle on exactly one slide, with arrow buttons and dot indicators (both driving and reading the same scroll position, so they can't disagree) for anyone navigating by click instead of drag. Each slide shows just the title and a "See more" link — no description or price — plus, when the advertiser provided them, floating WhatsApp/Contact icon buttons over the image; the image+title area (aside from the dismiss ✕) links to a public `/ads/[id]` detail page with the full description, every photo, and every contact method (`GET /advertisements/active/:id`). Dismissing a card only hides it for that page view — it's not persisted (previously written to localStorage, so one dismiss silently suppressed an ad for that visitor forever); advertisers are paying for impressions, and a permanent per-visitor opt-out worked against that. Admins get both a pending-only queue widget on the Moderation page (approve/reject) and a fuller Content > Advertisements tab (every status, filterable, plus **suspend** — for taking down an already-live ad for platform security); both surfaces now have a collapsed-by-default "Read full ad before deciding" expander (`AdvertisementFullDetails`) showing every photo and the complete description instead of the truncated preview, so an admin isn't approving an ad they've only seen a thumbnail and two lines of. The "advertisement pending review" notification links admins to the Moderation page's pending-advertisements queue (previously pointed at a route that didn't exist and 404'd).
- **Car Rentals**: Liberia has very few formal car-rental companies, so listing a car is peer-to-peer — **any signed-in user can list a vehicle**, the same way a driver signs up on Uber or a host signs up on Airbnb, with no Business or Place required first. Vehicles hang off `/account/my-car-listings` (`CarListingForm`, dual-mode create/edit: a required county picker, make/model/year/category/transmission/fuel/seats/price, optional driver fee/security deposit/minimum rental days/features/photos/description/pickup location/contact phone & WhatsApp) — the only gate is picking a county, not having a claimed business. A registered rental company that already has an approved `car_rental` `Business` can optionally link a listing to it (an advanced "link to my registered rental business" dropdown, defaulting to unlinked) so its fleet also shows up on that business's profile, but this is never required. `/car-rentals` is the public directory (`CarListingCard`/`CarRentalFilters`: category, transmission, county, seats, price, driver availability), `/car-rentals/[id]` the detail page (gallery, specs, price/deposit, features, a "Rented out by" card that shows the linked business's contact info when there is one and otherwise the individual owner's name plus their own direct phone/WhatsApp, reviews), and `/car-rentals/[id]/book` the dedicated booking page — same "full page, not a cramped tile" reasoning as `businesses/[slug]/book`. Renting a car is just a `Booking` with `carListingId` set (`BookingRequestSection` gained a third `carListing` target: a required return date, a driver-option checkbox when offered, and an optional pickup-location override — pricing is computed server-side and shown as a snapshot, not re-derived client-side) and reviewing one is just a `Review` with `carListingId` set (`ReviewsSection`'s third target). A car lister's incoming requests weren't reaching `/account/bookings` at all until fixed (they went straight to the backend inbox — `GET /bookings/car-listings/mine` — with no frontend caller anywhere): the page now has a third "Requests for my car listings" section (`getCarListingOwnerBookings`), shown whenever the account has listed at least one car, next to the pre-existing business/creator sections — same `BookingRow`/`BookingDetailModal` respond flow. The "my own requests" section's counterpart name also now falls back to the car's title when neither a business nor a creator owns the target (a direct-ownership car listing has neither), instead of the bare word "Listing". Submissions go straight to review, same lifecycle as Advertisements; admins get both a pending-queue widget on the Moderation page and a fuller Content > Car Rentals tab (every status, filterable, approve/reject/suspend, falling back to the listing owner's name wherever a linked business name isn't present); both surfaces now have `CarListingFullDetails`, the same collapsed-by-default "Read full listing before deciding" expander pattern as `AdvertisementFullDetails` — every photo, full description, every spec, and contact info instead of the one-line preview. A compact "Rent a car for your trip" tile on Home links to the directory. Renting for only part of a day is supported too: a lister can set an optional hourly rate (`pricePerHour`/`minRentalHours`/`driverFeePerHour` in `CarListingForm`, shown alongside the day-based fields wherever price/driver-fee is displayed), and `BookingRequestSection` shows a "By day / By hour" toggle whenever a listing has one — by-hour swaps the return-date input for start/end time inputs on the same day, shows a live estimated total as they're filled in, and sends `rentalUnit`/`requestedStartTime`/`requestedEndTime` instead of `requestedEndDate`. "My Bookings" shows the booked time range and the snapshotted `estimatedTotal` for either mode.
- **Restaurant menus**: a restaurant (or any other food-and-dining business) can list what it serves — a photo, the item's name, and its price, same three things a printed menu shows. `MenuItemsManager` (a per-item row: `SingleImageUploader` thumbnail, name/price/description/section edited inline on blur, an Available checkbox, plus an "Add a menu item" form, same immediate-per-item-mutation shape as `CreatorOfferingsManager`) lives in the owner's business dashboard's Menu tab (see "Business owner dashboard" below). Unlike Advertisements/Car Rentals/Business Content, a menu item never goes through admin review — same reasoning as a creator's service offerings: a $6 jollof rice listing carries none of the real-money/safety stakes a car rental or ad does, so an owner's edits are live on the public menu immediately. `MenuSection` (shared by the Place and business profile pages) renders the menu grouped into the owner's own freeform sections — "Appetizers", "Mains", "Drinks", whatever a business calls its own categories — in the order the owner set them, whenever the business has at least one item; toggling an item's Available checkbox off doesn't hide it, it shows with a "Sold out" tag instead, so a diner planning a visit still sees the whole menu and its prices. **The menu renders on the Place detail page** (`/places/[slug]`), not just the business profile — a visitor who clicks into a restaurant sees its menu (and amenities, via `PlaceKeyFacts`) as part of that place's own information, without ever needing to know or care that a separate `Business` record exists behind it; the business profile page keeps rendering it too, for anyone who lands there directly via an old link.
- **In-platform food ordering + order messaging**: on a restaurant's `MenuSection`, every in-stock item gets a quantity stepper — building a cart directly on the menu instead of a separate "order" page. A non-empty cart shows a sticky running total and a "Review order" step that login-gates the same way `EventTicketPurchase` does (browse and build a cart freely, log in only to actually send it); submitting calls `POST /businesses/:businessId/food-orders` and swaps the form for a confirmation screen linking to `/account/my-orders`. Price/name are never trusted from the client — the API snapshots them from the live menu at order time. `/account/my-orders` (`getMyFoodOrders`) is the buyer's order history: status, itemized total, cancel while pending/confirmed, and a "Message the restaurant" toggle that opens `FoodOrderMessageThread` inline per order. `FoodOrdersManager` is the restaurant owner's mirror, living in the business dashboard's Orders tab — incoming orders with confirm/decline (optional message to the buyer) and the same per-order message thread. `FoodOrderMessageThread` is a simplified `BookingMessageThread` sibling — send + the shared `MessageStatus` read-receipt tick, no edit/delete (an order's conversation is short-lived).
- **Business owner dashboard** (`/account/my-businesses`, product feedback Aug 2026: "the process to manage a business is kinda hidden and difficult to find ... instead of clicking here and there"): before this, an owner's only way to manage a claimed business was to find its public place page and scroll to a `#claim` anchor buried between "Nearby" and "Reviews," which then expanded into one long stacked form (profile edit, photos, business content, menu, orders all inline). Everything now lives in a dedicated dashboard, one click from the account hub's "My Businesses" quick-access card (or from a slim "Open business dashboard" link on the public place/business page's claim section) — `/account/my-businesses` lists every business the signed-in user manages; `/account/my-businesses/[id]` opens that business's own shell (`BusinessDashboardLayout`), a sidebar on desktop / horizontal scroll-tab strip on mobile driven by one shared nav config (`lib/business-dashboard-nav.ts`) so the two never drift apart. Tabs: **Overview** (pending-booking/pending-order counts, quick links into every other tab, the rejection-reason banner if applicable), **Profile & Photos** (`BusinessEditForm`, extracted out of the old inline claim-section code so it's reusable), **Place Details** (`PlaceDetailsManager`, editing `business.linkedPlace` — name, description, category, county/city, map location, tags, photos, hours, contact info; this absorbed the standalone `/account/my-places` page, which no longer exists — the underlying place and the business claiming it are one destination to manage now, not two), **Menu**/**Orders** (restaurant-only), **Bookings** (`BusinessBookingsManager`, built on the same `BookingRow`/`BookingDetailModal` pieces the combined `/account/bookings` page uses — extracted into `components/booking-ui.tsx` so neither page duplicates ~250 lines of modal/respond/cancel logic), **Updates** (`BusinessContentManager`), and **Analytics** (`AnalyticsSummary`, now scoped to one business instead of every claimed business stacked on one page). `useBusinessDashboard()` (React context set up by the layout) lets every tab page read the already-fetched `Business` and the auth token without each page re-deriving "which business is this id" itself.
- **Full moderation visibility (business claims &amp; content)**: two more pending-queue rows that used to show only a name and a couple of fields now expand to the complete submission before an admin decides — `BusinessFullDetails` (logo, every photo, description, phone/WhatsApp/email/website, hours, price range, services offered) on the Moderation page's "Pending business claims" and the Content > Businesses tab, and `BusinessContentFullDetails` (every photo, the full body instead of a 2-line clamp, validity window, link) on "Pending business content". Separately, the "Pending business claims" widget's only action used to be `VerifyBusinessControl` — which only grants a trust badge (`verificationStatus`) and never touched `Business.reviewStatus` at all, so there was no way to actually approve or reject a claim from that queue. It now also has `BusinessReviewStatusControl` (approve / request changes / reject / suspend, mirroring `BusinessesTab`'s own control) above the trust-badge control, which stays as a separate, clearly-labeled secondary action.
- **Featured Destination spotlight**: replaces the old "Featured this week" multi-card carousel with a single full-bleed hero banner (`FeaturedDestinationCard`) placed right below the Sponsored ad carousel — image, gradient overlay, title/description, and an "Explore" pill. It's a `SponsoredPlacement` (the same paid-placement pool admins manage at `/admin/sponsored-placements`), but rather than showing every active one in a shelf, Home picks ONE at random on every request (`Math.random()` at render time — this page already opts every fetch out of caching, so a plain refresh draws again just like a fresh visit). With more than one business paying for the same spotlight at once, this is effectively a rotating "bid for placement": nobody statically owns the slot, and traffic is shared out over time instead of crammed into one carousel. `/featured` lists every currently active placement (only linked from Home's "View all" when there's more than one to show) for a visitor who wants to see the full pool instead of whichever one they landed on.
- **Read receipts everywhere messages appear**: `MessageStatus` (`src/components/MessageStatus.tsx`, extracted from `BookingMessageThread`) is the shared "Sending… / Delivered / Viewed" tick-icon ladder shown under a sender's own message, driven by the message's `readAt` — `null` reads as Delivered, set as Viewed. Every in-platform message thread uses it: `BookingMessageThread`, `FoodOrderMessageThread`, and both support conversation pages (`/account/support/[id]`, `/admin/support/[id]`, which also call `markSupportMessagesRead` on load the same way the others call their own `markRead`).
- **Save icon on card thumbnails**: `SaveIconButton` — a compact circular bookmark toggle in the top-right corner of a place card's image (`PlaceCard`, `PlaceCardCompact`), using the same device-local save/bucket-list mechanism as the full `SaveButton` pill on the Destination Profile. Always a sibling of the card's `<Link>`, never nested inside it (a `<button>` inside an `<a>` is invalid HTML), so no click-propagation handling is needed either — the icon can't accidentally trigger the card's navigation.
- **Event locations, mapped like a Place**: `Event.latitude`/`longitude` (nullable, same `decimal(9,6)` shape as `Place`'s) let an organizer drop an exact pin the same way a self-service Place submission does — `NewEventForm` embeds the identical `PlaceLocationPickerLoader` (click/drag map, address search, "use my current location", manual entry) right below the freeform location-name field, both optional layers on top of `locationText`/`placeId` (see `Event`'s doc comment). The event detail page renders a non-interactive `EventMiniMapLoader` mini map plus a one-tap "Directions" button (`directionsLink`, the same Google Maps deep link `PlaceKeyFacts` uses) whenever coordinates resolve — from the event's own pin, or falling back to a linked catalog Place's coordinates when the event has none of its own. `eventJsonLd` includes the same `GeoCoordinates` schema.org block `placeJsonLd` already does, using the same fallback.
- **Trip chat**: `TripChatPanel`, mounted on every trip detail page a member can see, is a real-time-feeling group thread for the whole trip roster — text, photo attachments, one-level-deep reply quoting, a 7-emoji reaction picker (toggle on/off, must match `TripChatService.ALLOWED_REACTIONS` on the backend), and a Slack-style Sent/Delivered/Read ladder (`MessageStatus`'s `status` prop) computed from each member's read cursor rather than a per-recipient receipts table. Polls every 3s (shorter than `BookingMessageThread`'s 5s, the same no-websocket-infra reasoning, just for a livelier surface) and merges by message id, so edits/deletes/reactions/new messages from other participants show up without a page refresh. Sending is optimistic — a pending bubble with a client-generated `clientId` shows "Sending…" immediately and is reconciled once the real message comes back (from the POST response or, if that races, the next poll); a failed send offers Retry (same file, same upload) or Discard rather than silently vanishing. Own messages are editable/deletable (soft-delete → "This message was deleted", same convention as `BookingMessage`); join/leave/rename/cancel each drop a centered system message into the thread (no sender, not editable). Chat messages intentionally don't also fire a notification-bell entry — a deliberate scope decision, documented on `TripChatService.sendMessage` on the backend.
- **Public trip discovery beyond `/trips/community`**: the same `GET /itineraries/public?destinationPlaceId=` the community page already used gets two more callers now that it's server-fetchable via `lib/api.ts`'s `getPublicTrips` (not just the client-only `itinerary-api.ts` version `/trips/community` calls) — a "Trips heading here" section on the Place detail page (`/places/[slug]`, up to 6 public trips whose destination is that exact place, reusing `PublicTripCard`) and a "Trips you can join" horizontal rail on the Home feed (up to 6 of the most recent public trips platform-wide), both linking back to `/trips/community` for the full list.

## Known limitations

- `public/logo.png` is a full circular lockup rather than an icon-only mark; it reads busy at favicon size.
- Not every "you might want to know about this" event writes a notification yet — trip invitations, acceptances, and join requests/approvals/declines now write in-app notification rows alongside email, while business-content approval and creator verification remain email/UI-only for now.
- Social trips (public/private, request-to-join, Trip Admin, community discovery, group chat, destination-page/feed cross-linking) are built across three phases — see "Trip chat" and "Public trip discovery" below. Chat messages don't trigger header-bell notifications (a deliberate scope decision — see `TripChatService.sendMessage`'s doc comment on the backend) and there's no typing indicator.
- Unit test coverage (Jest) is a baseline — utilities and core components, not exhaustive. The Playwright suite covers the critical end-to-end flows (auth, search, reviews, bookings, admin moderation — see `e2e/README.md`), not every screen.
